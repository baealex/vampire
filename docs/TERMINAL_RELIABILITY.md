# 워크스페이스·원격 터미널 안정화

## 목표와 확인 범위

워크스페이스 전환과 원격 접속에서 실행 중인 작업, 화면 정합성, 입력 확인 상태를 보존한다. 저장소 변경량과 기기별 네트워크 속도가 커져도 작업량·대기열을 제한한다. 서버 코드, 실제 Git·tmux, 브라우저 회귀 테스트, 연결별 대역폭·지연·단절 중계기로 확인했다.

파일 탐색기는 처음부터 전체 디렉터리를 재귀 조회하지 않는다. 루트 직계 항목을 읽고 폴더를 펼칠 때 하위 목록을 요청한다. 다만 Git의 정확한 변경 파일 수를 구하는 `status --untracked-files=all`은 미추적 파일을 탐색하며, 이것은 파일 탐색기의 하위 폴더 API 요청과 별개다.

## 확인된 문제와 수정

| 문제 | 수정 |
| --- | --- |
| 한 기기의 이전 소켓이 남아 재접속 시 `Use this device` 표시 | 런타임별 임시 식별자와 증가하는 접속 번호로 같은 인증 세션·터미널의 이전 연결을 교체한다. 현재 소유자가 그 이전 연결일 때만 제어권을 이어받는다. |
| 자동 재시도 소진 후 네트워크·앱 복귀에도 수동 안내에 머묾 | 복귀 시 소진된 재시도 예산을 갱신한다. 진행 중인 재시도의 예산은 계속 초기화하지 않는다. |
| 인증·제한 종료가 탭 복귀 시 다시 자동 접속됨 | 재시도 금지 상태를 표시 여부와 분리한다. 명시적 재시도만 금지를 해제하며 서버 인증은 유지한다. |
| 느린 기기에 오래된 출력이 누적되어 최신 화면까지 약 27초 지연 | 기기별 WebSocket ping/pong으로 전송 확인을 받는다. 출력 예산을 사용하면 추가 델타를 보내지 않고, 확인 후 순서 경계가 있는 최신 화면으로 동기화한다. |
| 초기 화면 ACK 이전 512KiB 출력 대기열 초과가 재접속으로 이어짐 | 현대 프로토콜에서는 초과된 출력의 마지막 순서를 기록한다. 그 범위를 포함하는 스냅샷·동기화가 확보될 때까지 델타를 보내지 않고 최신 화면으로 복구한다. 구형 클라이언트의 종료 경로는 유지한다. |
| 새 파일마다 줄 수 계산용 Git 프로세스를 별도 실행 | 임시 인덱스의 intent-to-add와 한 번의 diff로 일괄 집계한다. 실제 인덱스·객체 저장소는 변경하지 않으며 임시 파일은 정리한다. Git 속성·바이너리·개행 없는 파일 처리도 유지한다. |
| 여러 기기의 동일 저장소 조회가 중복 실행 | 같은 저장소·커밋 페이지 크기의 진행 중인 스냅샷을 공유한다. 동시에 실행되는 Git status와 동일 폴더 목록도 공유한다. 완료된 결과를 오래 캐시하지 않아 후속 변경은 새로 읽는다. |
| 접은 폴더까지 매번 하위 목록 재조회 | 접은 폴더와 자손을 갱신 대상에서 제거한다. 다시 펼칠 때 최신 목록을 읽는다. 전체 접기·파일 트리 해제도 같은 처리를 한다. 진행 중인 요청이 나중에 완료돼 접힌 폴더를 되살리지 않도록 하고, 스냅샷에 이미 포함된 루트 목록은 다시 요청하지 않는다. |
| 떠난 워크스페이스의 읽기·예약 갱신이 이어짐 | 읽기 요청을 AbortSignal로 취소하고 후속 갱신을 중단한다. 이미 서버에서 실행 중인 공유 Git 작업까지 취소하는 것은 아니다. |

저장소 상태 감시는 같은 작업 경로의 소켓끼리 공유하고 마지막 소켓이 닫히면 해제한다. 이벤트를 모아 최소 1초 간격으로 갱신하며, 상태 감시가 불가능한 경우 10초 보조 조회를 사용한다. 저장소 패널이 닫혀 있으면 전체 스냅샷 갱신을 요청하지 않는다. 변경 내용은 파일 수가 그대로여도 달라질 수 있으므로 수가 같다는 이유만으로 갱신을 없애지는 않는다.

## 보존하는 계약

- 확인되지 않은 명령을 자동 재전송하지 않는다. 전달 확인 유실 시 작성 내용을 복구할 수 있다.
- 명령 전달 확인은 tmux 입력 전달의 확인이며 에이전트 작업 완료를 의미하지 않는다.
- 재접속이 실제 다른 기기의 제어권을 자동으로 빼앗지 않는다. 여러 기기 사이의 명시적 제어권 이동은 정상 동작이다.
- 출력 조각을 건너뛰었으면 그 범위를 포함하는 권위 있는 화면을 먼저 적용한다. 이후 델타는 해당 순서 이후의 것만 보낸다.
- 출력 제어는 구독자별이다. 느린 기기의 pong을 공유 tmux 작업 안에서 기다리지 않는다.
- 32KiB 출력 예산은 프레임 경계에서 적용한다. 개별 프레임은 이를 넘을 수 있고 기존 8MiB 프레임 제한을 따른다. 서버의 스냅샷 대기열 512KiB, 소켓 2MiB, 브라우저 대기열 제한은 유지한다.
- WebSocket pong은 네트워크 수신 확인이지 DOM 표시 완료가 아니다. 브라우저 자체의 출력 상한도 계속 필요하다.
- 깊은 히스토리처럼 실제로 요청한 데이터가 큰 경우 그 전송 비용은 남는다. 느린 회선에서 모든 데이터를 즉시 보여준다고 보장하지 않는다.

## 측정

임시 Git 저장소에 두 줄짜리 새 파일을 만들고 동일한 전체 스냅샷 API를 변경 전후 호출했다. `GIT_TRACE2_EVENT`의 프로세스 시작 기록으로 실행 횟수를 확인했다. 로컬 단일 측정이며 보장 지연이나 통계적 백분위가 아니다.

| 새 파일 | 변경 전 | 변경 후 | Git 실행 횟수 전 → 후 |
| --- | ---: | ---: | ---: |
| 100 | 679ms | 266ms | 109 → 11 |
| 500 | 3,035ms | 436ms | 509 → 11 |
| 2,000 | 10,768ms | 1,325ms | 2,009 → 11 |

줄 수 결과는 각각 200·1,000·4,000행으로 같았다. 네 기기 중 하나에만 연결별 256Kbps·왕복 페이로드 지연 1초를 적용한 약 3.1MB/4초 출력 시험에서는 최신 화면 도달이 기존 26.8초에서 수정 후 약 4.9~7.4초로 줄었다. 네 기기 모두 접속 1회를 유지했고 후속 입력 후 실제 tmux 화면과 일치했다. 상세 조건과 최신 검증 결과는 [원격 연결 검증](TERMINAL_NETWORK_VALIDATION.md)을 따른다.

## 진단과 한계

브라우저는 `vampire:terminal-connection` 이벤트에 연결 단계·시도 번호·경과 시간·종료 코드를 제공한다. 알려진 종료 이유만 보존하며 임의 문자열은 `unclassified`로 처리한다. 경로, 인증 정보, 터미널 내용은 포함하지 않는다. 진단을 자동 저장하거나 외부 전송하지 않는다.

```js
window.terminalConnectionEvents = [];
window.addEventListener('vampire:terminal-connection', (event) => {
  window.terminalConnectionEvents.push(event.detail);
  if (window.terminalConnectionEvents.length > 128) window.terminalConnectionEvents.shift();
});
```

`ready`는 서버 준비 메시지 수신 시점이며 실제 화면 표시나 명령 완료 시점이 아니다. 종료 코드 1006만으로 서버 heartbeat·전송 혼잡·망 단절 중 원인을 확정할 수 없다. 실제 사용자 단절의 원인이 이 코드 수정과 동일했는지도 증거 없이 단정하지 않는다.

실제 모바일 운영체제의 절전·메모리 회수, Wi-Fi↔셀룰러 이동, 패킷 손실·TCP 재전송, 수 시간·수 일 지속 사용은 이 자동 검증 범위 밖이다. 사용자 서비스와 실행 중인 터미널은 재시작하거나 배포하지 않았다.
