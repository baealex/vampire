# Release notes convention

This document defines the format for Vampire GitHub Release notes. Release
notes are written for people deciding whether to upgrade, not as a copy of the
commit log.

## Goals

- Explain the user-visible outcome of a release.
- Make releases easy to scan and compare over time.
- Keep installation and comparison links correct for every version.
- Separate product changes from internal implementation and release work.

## Language and voice

- Write public release notes in English, matching the rest of the project
  documentation.
- Use present-tense, outcome-first verbs: `Add`, `Improve`, `Keep`, `Fix`, or
  `Prevent`.
- Describe what a user can do or observe. Avoid commit hashes, internal issue
  names, CI details, and implementation-only refactors unless they affect
  compatibility, security, performance, or maintenance users can notice.
- Keep each bullet to one focused outcome. Combine closely related technical
  details when they serve the same user-facing result.
- Do not use emojis, autogenerated contributor sections, or unexplained
  project-internal terminology.

## Structure

Use this order for every release:

1. `## Highlights` — two to four concise bullets describing the most
   important upgrade reasons.
2. One or more topical sections — use the approved area names below and add
   only sections relevant to the release.
3. `## Quality` — include when the release adds meaningful coverage,
   reliability, compatibility, or packaging safeguards.
4. `## Install` — always include the exact versioned commands.
5. `## Full changelog` — always include a compare link to the previous tag;
   use `Initial release.` for `v0.1.0`.

The release title is exactly `vX.Y.Z`. Do not repeat the version in the body
headline. Draft the body locally at the ignored `docs/RELEASE_DRAFT.md` path,
then create an annotated tag from that file with `--cleanup=verbatim`. Tagged
releases are blocked when the tag message does not follow the required
structure. Delete the local draft after a successful release. GitHub Releases
are the historical source for published notes.

### Approved topical sections

Prefer these names so related releases use the same vocabulary:

- `Workspaces`
- `Terminal`
- `Repository`
- `Mobile`
- `Notes and Automation`
- `System Status`
- `Server and Security`
- `Fixes`
- `Release Safety`

Use `Quality` for test coverage and reliability rather than as a catch-all for
product features.

## Markdown template

```md
## Highlights

- [Most important user-visible outcome]
- [Second upgrade reason]

## [Relevant Area]

- [Focused outcome]
- [Focused outcome]

## Quality

- [Meaningful coverage, compatibility, reliability, or packaging improvement]

## Install

Run directly:

```sh
npx vampire@X.Y.Z --token-file ~/.config/vampire/token
```

Or install it globally:

```sh
npm install --global vampire@X.Y.Z
```

## Full changelog

[Compare vPREVIOUS...vX.Y.Z](https://github.com/baealex/vampire/compare/vPREVIOUS...vX.Y.Z)
```

Omit optional topical sections and `Quality` when they do not apply, but keep
`Highlights`, `Install`, and `Full changelog` in every release. The first
release uses `Initial release.` instead of a compare link.

## Writing checklist

Before publishing a release note:

- Confirm every claim against the changes between the previous and current
  tags.
- Put the largest user-facing changes first in `Highlights`.
- Check that all bullets use the same present-tense voice.
- Use the exact release version in both install commands.
- Link `Full changelog` to the correct previous tag and current tag.
- Remove autogenerated `Full Changelog`, contributor, and PR-only sections.
- Make sure the note still reads clearly without opening the commit history.
