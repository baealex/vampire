# 원격 연결·저장소 검증 기록

## 문서 성격

이 문서는 0.27.x 개발 중 연결 복구와 저장소 갱신 병목을 조사한 기록이다. 당시에는 TCP 중계기, 다기기 브라우저, 지속 출력, tmux와 xterm 행 비교를 포함한 부하 E2E를 사용했다.

그 부하 시험은 외부 브라우저·터미널 구현의 내부 동작과 로컬 네트워크 모사를 검증하는 데 비용이 컸고, 환경에 따라 흔들렸다. 따라서 `e2e/terminal-network.ts`와 관련 부하 시나리오는 제거했으며, 아래 수치는 현재 회귀 기준이 아니다.

## 조사에서 확인한 결론

- 출력 전송은 연결별 수신 확인 후 최신 상태를 동기화해야 한다.
- 초기 스냅샷이나 명령 확인이 지연·유실돼도 미확인 초안은 보존하고 명령을 임의로 재전송하지 않아야 한다.
- 재접속은 이전 연결을 정리하고 다른 기기의 제어권을 빼앗지 않아야 한다.
- 저장소 조회는 진행 중인 파일 열기를 재시작하지 않고, 동시 조회 작업을 불필요하게 중복하지 않아야 한다.

이 결론을 보장하는 서버·상태·연결 계약은 Node/React 테스트와 앱 코드에 남아 있다. 브라우저 테스트는 이 계약의 사용자 결과만 확인한다.

## 현재 검증 범위

| 계층 | 명령 | 목적 |
| --- | --- | --- |
| 타입·구조 | `pnpm check` | 타입, 아키텍처, 디자인 시스템 계약 |
| 서버·공유 로직 | `pnpm test:node` | 연결, 저장소, 상태 계약 |
| React | `pnpm test:react` | 애플리케이션 상태와 컴포넌트 동작 |
| 릴리즈 브라우저 | `pnpm test:e2e:release` | 핵심 설정·자동화 흐름과 보안 사용자 경계 |
| 전체 브라우저 | `pnpm test:e2e` | 수동 품질 점검용 보조 검증 |

릴리즈 E2E에는 렌더러의 프레임 수, xterm 내부 행 구조, tmux와 브라우저의 행별 동일성, 네트워크 속도별 처리량 같은 검사를 넣지 않는다. 그런 동작은 외부 라이브러리와 실행 환경의 책임이며, 앱은 공개 계약을 통해 검증한다.

## 남는 한계

실제 모바일 운영체제의 절전·메모리 회수, 무선망 이동·공유 회선 혼잡·패킷 손실, 수 시간 이상의 사용은 로컬 자동화로 보장하지 않는다. 이런 조건이 필요하면 별도 운영 관찰이나 수동 검증으로 분리한다.

저장소 성능의 상세 수치와 과거 측정 조건은 이 문서의 이전 버전에 기록돼 있었으나, 현재 테스트 결과나 제품 보장으로 해석하지 않는다.
