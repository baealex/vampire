# 핵심 워크플로우 개선 기록

## 목표와 판단 기준

워크스페이스 열기 → 입력·전송 → 출력 확인 → 파일·백그라운드 작업 확인 → 다른 워크스페이스로 전환·복귀하는 흐름을 대상으로 한다.

| 흐름 | 보호할 동작 |
| --- | --- |
| 입력·전송 | 높이가 고정된 입력창, 한글 조합과 여러 줄 작성, 명확한 입력 전환, 전송 상태와 초안 복구 |
| 출력 확인 | 메시지 전송이 pane 크기를 바꾸지 않음, 연속 출력이 전달됨, 최종 웹 화면이 tmux와 일치함 |
| 전환·복귀 | 워크스페이스별 초안·입력 포커스 유지, 기기 간 제어권과 화면 크기 복구 |
| 보조 작업 | 저장소 패널과 백그라운드 작업이 메인 터미널을 불필요하게 변경하지 않음 |
| 작은 화면 | 입력창과 모드 전환 접근 가능, 최소 출력 행 확보, 가로 넘침 없음 |

## 발견한 문제와 수정

### 전송 안내가 실제 출력 지연을 유발

`ComposerSubmissionRecovery`가 입력창 위의 일반 문서 흐름에 삽입되어, 전송 안내가 나타나고 사라질 때마다 터미널 높이가 바뀌었다. 브라우저는 그 변화를 tmux에 전달했고, 서버는 화면 크기 변경에 따른 재동기화를 수행했다.

연속 출력을 전송 직후 시작하는 재현에서 111×26 → 111×23 → 111×26의 두 크기 변경이 발생했다. 서버는 재동기화 중 일반 출력 전달을 억제하고 약 1초 간격으로 최신 화면을 전달했다. 이 조건에서 100개 출력 표식 중 실시간 수신·화면 관측에 남은 표식은 6개였다. tmux의 최종 화면은 웹 화면과 일치했다.

전송·복구 안내를 입력 도크 위에 겹쳐 표시하도록 바꾸고, 높이 제한과 내부 스크롤을 적용했다. 안내가 나타나도 pane 크기가 유지되므로, 같은 재현에서 100개 표식이 모두 전달됐다. 전송 확인 대기, 확인 유실 후 초안 보존, 새로고침 후 복구는 유지한다.

서버의 출력 순서 제어, 화면 복원 확인, 파서·소켓 대기열 상한은 유지했다. 이번에 확인한 병목은 전송 안내에 의해 불필요한 리사이즈 경로가 실행되는 문제였다.

### 입력창의 상시 두 줄 구성

입력 모드·템플릿·미리보기·단축키 안내가 별도 줄을 차지했다. 기본 글꼴 16px의 데스크톱 CSS 계산에서 입력창 예약 높이는 약 81px이었다.

데스크톱에는 모드 전환, 입력, 기록, 이미지, 전송을 한 줄로 배치했다. Compose의 상시 미리보기와 템플릿 바이패스, 데스크톱 더보기는 제거했다. 상시 단축키 안내 문장은 없애고 `Switch input` 버튼 안에 운영체제에 맞는 전환 단축키를 표시했다.

입력창 예약 높이는 약 48px로 줄었다. 여러 줄을 작성해도 입력 영역은 40px 높이를 유지하고 가운데 한 줄의 textarea 안에서 스크롤한다. 세로 여백을 스크롤 영역 밖에 두어 현재 줄이 위아래로 치우치지 않게 했다. 위로 늘어나 터미널 출력을 덮지 않는다. Shift+Enter는 브라우저의 기본 줄바꿈을 사용하므로 커서가 새 줄로 이동할 때 스크롤도 따라간다. 작은 화면에서는 모드 버튼의 아이콘과 접근성 이름을 유지하며, 화면 높이를 이유로 모드 전환을 숨기지 않는다.

폭 512px 이하에서는 기록·이미지를 `More message actions`로 묶어 입력 폭을 확보한다. 320px 화면에서도 입력칸 폭이 150px 이상이고, 빈 입력창의 실제 높이가 52px 이하인지 검증한다. 기록은 입력창의 동작 버튼 위에 배치하고 닫을 때 포커스를 복원한다. 입력칸을 다시 누르면 팝업이 닫혀 편집을 이어갈 수 있다.

### 데스크톱 보조 키와 표시 설정

마우스를 주 입력 장치로 사용하는 데스크톱에서는 보조 키 줄을 숨기고, 터치 환경에서는 유지한다. 빈 Compose의 방향키·Enter·Esc 전달에 Backspace를 추가했다. 초안이 있으면 편집 동작을 유지한다. 터미널에 포커스가 있으면 xterm의 직접 입력을 사용한다.

스크롤 이동은 터미널 또는 빈 Compose에서 Shift+PageUp/PageDown, Shift+Home/End로 사용할 수 있다. 글자 크기는 설정의 Appearance에서 변경하고 기존 브라우저 저장 값을 그대로 사용한다. 캐시된 터미널로 돌아올 때도 변경된 크기를 반영한다.

Compose에는 일반 UI 글꼴을 사용하고, 줄 높이를 기준으로 위아래 여백을 동일하게 맞췄다. 단축키 설정은 동작별 행과 줄바꿈되지 않는 키 조합으로 정리했다.

### Ask agent 진입 위치

노트·백그라운드·오토메이션·위젯의 진입 버튼을 상단 작업 영역의 아이콘과 `Ask agent…` 텍스트로 맞췄다. 네 화면은 기존 `AskAgentDialog`를 계속 사용한다. 노트의 저장 후 전달, 위젯의 대상 워크스페이스 선택, 실행 중인 프로세스가 없을 때의 비활성화 등 작업별 조건은 유지한다.

## 출력 측정 방법과 관측 결과

2026-09-06, Node 24.19.0, tmux 3.7c, Playwright 1.62.0의 로컬 Chromium 환경에서 측정했다.

실제 tmux 안의 프로세스가 20ms 간격으로 100회 출력한다. 매회 한글·ANSI 색상이 포함된 20행과 생성 시각 표식을 출력한다. WebSocket 수신 시각과 브라우저의 화면 갱신 주기에서 처음 관측한 DOM 시각을 기록한다. 출력 후 실제 tmux 화면과 웹의 모든 표시 행을 비교하고, 다음 입력의 결과도 확인한다.

| 항목 | 수정 후 관측값 |
| --- | --- |
| 생성한 표식 / 수신한 표식 / DOM에서 관측한 표식 | 100 / 100 / 100 |
| 출력 생성 → WebSocket 수신 | 중앙값 2ms, 95백분위 3ms, 최대 15ms |
| 출력 생성 → DOM 관측 | 중앙값 15ms, 95백분위 19ms, 최대 31ms |
| 새 출력이 관측된 화면 갱신 사이 간격 | 중앙값 24ms, 최대 26ms |
| 후속 입력 → 결과 확인 | 43ms |
| 측정 중 입력창 때문에 발생한 크기 변경 | 0회 |

이 수치는 해당 부하와 로컬 연결에서의 관측값이다. DOM 관측은 중간 프레임을 건너뛸 수 있으며, 수신 콜백과 입력 결과 확인에는 테스트 도구의 관측 비용이 포함된다. 별도 서버 파서만의 지연, 원격 네트워크 성능, 최대 처리량을 나타내지는 않는다. 시간 수치는 진단 자료로 기록하고, CI의 고정 속도 합격선으로 사용하지 않는다.

## 재현과 회귀 검증

출력 전달 진단:

```sh
pnpm exec playwright test --project=desktop-chromium -g 'measures sustained tmux'
```

해당 테스트 결과 폴더에 `terminal-output-latency.json`과 `terminal-deliveries.json`이 생성된다. 전달 기록에는 메시지 종류, 크기 변경, 출력 표식과 관측 시각이 포함된다. 테스트 서버와 tmux 소켓은 E2E 전용 환경을 사용한다.

전송 상태·초안 복구·입력창 높이:

```sh
pnpm exec playwright test --project=desktop-chromium -g 'keeps Compose drafts until|keeps Composer fixed'
```

작은 화면과 모바일 입력:

```sh
pnpm exec playwright test --project=mobile-chromium --project=mobile-firefox --project=mobile-webkit -g 'extreme keyboard-height|keeps direct terminal input|keeps a Compose draft focused|preserves mobile composition'
```

코드 검증:

```sh
pnpm check
pnpm test:node
pnpm exec vitest run --config vitest.config.ts src/lib/features/terminal
```

## 다음 성능 점검에서 구분할 조건

### 장문 작성과 입력 제한

- Compose 전체화면 편집과 상시 프리뷰를 제거했다. 고정 높이 입력창, 내부 스크롤, 클릭 동작 없는 `+ N lines` 표시를 유지한다.
- 템플릿을 한 번 건너뛰는 기능과 단축키·저장 상태 복원을 제거하고 설정된 템플릿을 적용한다. 설정의 템플릿 미리보기는 예시 입력칸 없이 `[Your message]` 자리와 변수 적용 결과를 보여준다.
- 입력 한 건의 상한은 UTF-8 64KiB이며, 직렬화한 WebSocket 메시지는 72KiB까지다. 줄바꿈·이스케이프 문자 비중에 따라 메시지 상한에 먼저 도달할 수 있다.
- Compose는 전송 전에 크기를 검사하고 초안을 유지한다.
- 직접 터미널 입력은 브라우저에서 한 메시지로 보내며, 서버가 수신한 다음 tmux 제어 명령을 4KiB 단위로 나눈다. 이 분할은 앞단의 WebSocket/입력 크기 제한을 우회하지 않는다.
- Workspace note의 중복 설명 `Keep the next step here.`를 제거했다.

### 성능 측정 조건

- 원격 네트워크 지연·대역폭과 느린 브라우저에서의 대기열 증가·복구.
- 여러 pane이 동시에 많은 출력을 내는 경우의 서버 파서 CPU·메모리와 최대 처리량.
- 실제 모바일 기기의 소프트웨어 키보드·IME 동작. 브라우저의 모바일 에뮬레이션과 별도로 확인한다.
- 시스템 상태 바의 상시 노출 여부는 사용 빈도와 조작 수를 비교해 결정한다.

## 검증 결과

- 전체 Node 테스트 406개 통과.
- 터미널 컴포넌트 테스트 73개 통과.
- 데스크톱·모바일 핵심 흐름 34개 E2E 통과. 작은 화면의 메뉴를 보강한 뒤 해당 변경과 데스크톱 입력창을 대상으로 8개 E2E를 추가 검증했고 모두 통과했다.
- 모바일 메뉴의 미리보기·템플릿 변경·기록 검색·이미지 선택, 팝업 닫기와 편집 복귀를 Chromium·Firefox·WebKit에서 확인했다.
- `pnpm check` 통과. 아키텍처·디자인 시스템 검사와 Svelte·TypeScript 검사를 포함한다.
- `pnpm format:check`, `git diff --check` 통과.

후속 사용성 조정에서는 관련 컴포넌트 66개와 데스크톱·모바일 E2E 9개가 통과했다. 고정 높이 및 기본 줄바꿈으로 변경한 뒤에는 입력 컴포넌트 33개와 관련 E2E 7개를 추가 확인했다. E2E에는 설정에서 글자 크기를 변경한 뒤 캐시된 터미널로 복귀·새로고침하는 흐름, 줄바꿈 뒤 커서 스크롤, 모바일 IME·메뉴 흐름이 포함된다.

상시 프리뷰·전체화면 편집 제거 후 입력 컴포넌트 26개와 설정 컴포넌트 12개, 단축키 Node 테스트 1개를 통과했다. 설정 템플릿 적용과 고정 높이 입력창의 데스크톱 E2E 2개, 더보기 메뉴의 모바일 Chromium·Firefox·WebKit E2E 3개를 확인했다. `pnpm check`와 아키텍처 검사도 통과했다.

바이패스와 데스크톱 더보기 제거 후 컴포넌트 30개, 단축키 Node 테스트 1개, 데스크톱·모바일 E2E 4개가 통과했다. 브라우저에 남은 바이패스 설정이 전송에 영향을 주지 않는지, 모바일에서 연 더보기가 데스크톱 폭으로 전환하면 닫히는지 검증했다. 최종 `pnpm check`와 `pnpm format:check`도 통과했다.
